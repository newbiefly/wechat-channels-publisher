# 登录闸门

视频号的登录态随时可能失效（实测：19:48 还在发，21:10 就掉回 `login.html`，两小时不到）。所以每次发布前都要过这道闸门。

## 一、怎么判定"需要登录"

四条证据，**命中任意一条就停**，不许试探性地点页面上的任何东西：

| 证据 | 怎么拿 | 可靠度 |
|---|---|---|
| 输出里有 `[NEED_LOGIN]` | 读后台任务输出 | 高（脚本主动打的标记） |
| `status.json` 的 `state == "need_login"` | `py -3 -c "...sph_env.read_status()"` | 高（结构化，无需解析文本） |
| 退出码 2 | 命令返回码 | 高 |
| URL 含 `/login.html` | 只有手动调试时才看 | 中（页面可能在跳转中） |

反向判据（脚本内 `ensure_login` 用的）：**URL 不含 `login`，且 `wujie-app` 的 shadowRoot 里能查到 `.label` 文案「视频描述」**。两条都满足才算登录成功——只看 URL 会在页面还在加载时误判。

> 不要用"页面上有没有二维码"判断。二维码在 `open.weixin.qq.com` 的 iframe 里，跨域读不到 DOM，只能靠 URL 和表单渲染状态。

## 二、提示用户的话术（三段，缺一段就卡）

```
视频号登录态过期了，已弹出一个 Chrome 窗口停在扫码页。
请用【能管理这个视频号的那个微信】扫码；
扫完还要在手机上点一次「确认登录」，只扫码不确认不会进去。
扫完回我一声就行，我这边也盯着，最多等 3 分钟。
```

为什么必须写"手机上点确认"：微信扫码后手机会弹二次确认页，多数人以为扫完就好了，结果页面一直停在二维码上，白等 5 分钟。

## 三、等待节奏

进程是阻塞的（`ensure_login` 里 `while` 循环），**不要为了"看一眼"反复重跑脚本**——重跑会重启 Chrome、换一个新二维码，用户手上那个就失效了。

| 时间点 | 动作 |
|---|---|
| 启动后 20–30 秒 | 读一次输出/状态，确认是 `need_login` 还是已经 `running` |
| 之后每 10–15 秒 | 读 `status.json`，比读输出便宜 |
| 每 60 秒 | 可以给用户报一次剩余时间，别更密（刷屏） |
| 到达 `--wait` 上限 | 脚本自己退出（码 2），报告"本次没有发布任何内容" |

默认 5 分钟对多数人够用。用户明显不在电脑前（几轮都不动）就直接停下，别耗满。

## 四、异常分支

| 现象 | 原因 | 处理 |
|---|---|---|
| 用户说"扫了"，页面还在二维码 | 没点手机上的「确认登录」 | 让他再扫一次并确认；不要重启脚本 |
| 页面显示「加载失败，点击重试」 | 二维码过期（约 2–3 分钟） | **让用户点那个「点击重试」**，不重跑脚本 |
| 扫码后跳"该微信号没有视频号" | 微信用错了账号 | 换能管理该视频号的那个微信 |
| 连续 3 轮都进不去 | 网络/风控/账号异常 | 停下报告，让用户手动在该 Chrome 窗口登录后回复，再继续原命令 |
| 超时退出后想继续 | 登录态没拿到 | 直接重跑原命令即可，不会重复发布（发布记录会拦） |

## 五、登录态能撑多久

- 存在 `<data_dir>/sph-profile/`（独立 Chrome 配置），Cookie 持久化，关掉浏览器不丢。
- 实测寿命**不固定**：有时几小时就掉，有时能撑几天。平台按风控节奏回收，不要假设"早上扫过下午就不用"。
- 因此**每次发布前先跑 `login.py` 探一次**（已登录时 3 秒返回，比白等 5 分钟划算）。

## 六、红线

- 不导出、不打印 Cookie，不把 `sph-profile/` 复制到别处或提交进仓库。
- 不尝试绕过扫码（改 UA、伪造 cookie），只等人。
- 换账号 = 换 profile，换完必须重新扫码；不要两个账号共用一个 profile。
